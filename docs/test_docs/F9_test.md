# F9 Streamlit 产品集成测试用例方案

## 1. 测试目标

F9 的目标是把 F1 到 F8 的全部能力整合成一个完整、可用、可演示的 Streamlit 多页面应用。它关注的不是某一个领域服务是否正确，而是用户能否从零开始完成完整学习闭环：

```text
填写目标
  -> 生成学习计划
  -> 查看并编辑任务
  -> 上传资料并问答
  -> 标记进度
  -> 复盘并动态调整
  -> 导出计划
  -> 刷新后恢复状态
```

F9 测试重点包括：

- 多页面结构是否完整。
- 页面之间的状态是否连续。
- 页面是否只调用 Application UseCase，不直接调用 LLM SDK、SQL、Milvus SDK 或具体 Agent 节点。
- Fake 环境下是否能稳定走通端到端流程。
- Real 环境下是否能通过真实 LLM / RAG / PostgreSQL 完成主流程或给出可理解错误。
- 关键操作是否更新 Session State 和持久化状态。
- 空状态、错误状态、刷新恢复、保存失败、导出失败等边界是否可控。
- 用户能否不依赖复杂说明完成主流程。

## 2. 需求来源

### 2.1 PRD 相关要求

PRD 中 F9 相关要求包括：

- 前端应用使用 Streamlit。
- 页面需要覆盖：
  - 学习目标配置
  - 学习计划看板
  - 资料问答
  - 复盘调整
  - 导出能力
- 用户可以输入学习目标并生成完整学习计划。
- 用户可以查看、编辑任务并标记完成状态。
- 用户可以上传资料并进行资料问答。
- 用户可以根据完成情况生成复盘和调整建议。
- 用户可以导出学习计划。
- 刷新后核心数据不丢失。
- 页面无需复杂说明即可使用。
- 任务列表易于查看和修改。
- 图表能直观反映学习进度。
- 调整后的计划需要用户确认后保存。

### 2.2 features.md 相关要求

features.md 对 F9 的要求包括：

- 将 F1 到 F8 集成为完整可用的 Streamlit 应用。
- 页面结构至少包含：
  - 首页
  - 学习目标配置页
  - 学习计划看板页
  - 资料问答页
  - 复盘调整页
- Session State 至少管理：
  - `study_goal`
  - `study_plan`
  - `selected_plan_id`
  - `materials`
  - `last_review_report`
  - `errors`
- 页面流转：

```text
学习目标配置
  -> 生成学习计划
  -> 学习计划看板
  -> 资料问答，可选
  -> 复盘调整
  -> 导出
```

- 页面不直接调用 LLM SDK。
- 页面不直接写 SQL。
- 页面不直接调用 Milvus SDK。
- 页面只调用 Application UseCase。
- 长任务显示加载状态。
- 错误展示为用户可理解的信息。
- 关键操作完成后更新 Session State。
- 手动测试主流程可以完整走通。
- 没有学习目标时不能生成计划。
- 没有学习计划时看板给出提示。
- 上传资料后资料问答可用。
- 更新进度后复盘可用。
- 导出按钮可下载文件。

## 5. 测试环境

### 5.1 Fake 环境

Fake 环境用于自动化测试和本地快速验收：

```env
USE_REAL_LLM=false
USE_REAL_RAG_STORE=false
USE_POSTGRES_PERSISTENCE=false
```

预期：

- 不依赖真实 DeepSeek / OpenAI / Qwen。
- 不依赖真实 Milvus。
- 不依赖真实 PostgreSQL。
- 可以用 InMemory repository 和 Fake LLM / Fake RAG 走通主流程。
- 测试稳定、速度快、可在 CI 中运行。

### 5.2 Real 环境

Real 环境用于手动验收或带标记的 integration/manual 测试：

```env
USE_REAL_LLM=true
DEEPSEEK_API_KEY=...
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-chat
USE_REAL_RAG_STORE=true
MILVUS_URI=http://localhost:19530
MILVUS_COLLECTION=study_materials
USE_POSTGRES_PERSISTENCE=true
DATABASE_URL=...
```

预期：

- 真实 LLM 可以生成计划和复盘。
- 真实 RAG 可以上传、检索、问答。
- 真实 PostgreSQL 可以刷新恢复计划和任务状态。
- Real 测试不应阻塞普通 CI，可使用 `manual` 或 `integration` marker。

- 不在启动时执行长耗时任务。

### TC-F9-110 主流程完成后状态可清理或重新开始

**步骤**：
1. 完成一次主流程。
2. 回到目标配置页生成新计划。

**预期结果**：
- 新计划可以替换旧计划。
- 旧的 pending 调整不会污染新计划。

## 21. 阶段十三：视觉设计、图表与信息架构

### TC-F9-111 所有页面具备统一且专业的视觉设计

**步骤**：
1. 依次打开首页、目标配置、计划看板、资料问答、复盘调整、计划导出页面。
2. 检查页面布局、色彩、间距、标题层级、按钮样式、表格样式和反馈信息。

**预期结果**：
- 页面不再是 Streamlit 默认控件堆叠感。
- 各页面有统一的视觉语言。
- 信息层级清晰，重要操作突出。
- 页面看起来专业、干净、有产品感。
- 不使用过度装饰影响效率。

### TC-F9-112 首页颜值高且有明确引导性

**步骤**：
1. 打开首页。
2. 从新用户视角判断是否知道下一步该做什么。

**预期结果**：
- 首页首屏视觉质量高。
- 首页明确展示产品价值和主流程入口。
- 用户能快速理解：
  - 先配置学习目标
  - 再生成学习计划
  - 后续可资料问答、复盘、导出
- 首页有清晰主按钮或导航入口。
- 首页不只是简单文字说明。

### TC-F9-113 首页能承接空状态和已有计划状态

**步骤**：
1. 无计划时打开首页。
2. 已有计划时打开首页。

**预期结果**：
- 无计划时引导用户创建学习目标。
- 已有计划时引导用户继续查看看板、复盘或导出。
- 首页不会让用户重复迷路。

### TC-F9-114 看板图表比基础统计更有洞察

**步骤**：
1. 生成包含多天、多周、多主题任务的计划。
2. 打开看板页面。

**预期结果**：
- 不只显示简单 metric。
- 至少提供若干实用图表，例如：
  - 每日学习分钟趋势
  - 每周学习负载柱状图
  - 任务状态分布
  - 主题/知识点任务占比
  - 完成率趋势
- 图表能辅助用户判断时间负载和进度风险。

### TC-F9-115 复盘页面图表能解释进度问题

**步骤**：
1. 构造部分完成、延期和薄弱点场景。
2. 打开复盘调整页面。

**预期结果**：
- 复盘页面提供直观图表或可视化摘要，例如：
  - 完成/未完成/延期分布
  - 薄弱知识点排行
  - 延期任务时间轴
  - 调整前后任务日期对比
- 用户能看出为什么需要重排。

### TC-F9-116 资料问答页面展示资料状态和引用质量

**步骤**：
1. 上传多份资料。
2. 完成一次问答。

**预期结果**：
- 页面展示资料处理状态。
- 页面展示资料数量、chunk 数或可检索状态。
- 引用来源展示清晰，不只是一段纯文本。
- 用户能判断答案依据来自哪份资料。

### TC-F9-117 导出页面提供清晰预览和格式差异

**步骤**：
1. 打开导出页面。
2. 查看 Markdown / HTML 导出区域。

**预期结果**：
- 页面说明不同导出格式的适用场景。
- HTML 导出有预览或效果说明。
- 下载按钮布局清晰。
- 用户知道当前导出的是最新计划。

### TC-F9-118 页面是否需要整合有明确判断

**步骤**：
1. 评估现有页面数量、导航路径和用户完成主流程的点击成本。
2. 比较独立页面与整合页面的体验。

**预期结果**：
- 如果页面独立更清晰，则保持多页面结构，但导航和状态提示要连贯。
- 如果某些页面割裂或跳转成本过高，则提出并实现整合方案。
- 整合判断基于用户完成主流程的舒适度，而不是单纯减少页面数。
- 不为了整合而把页面做得拥挤。

### TC-F9-119 页面整合后不破坏功能边界

**步骤**：
1. 如果实现页面整合，检查整合后的代码和交互。

**预期结果**：
- 页面可以整合，但 Application / domain / infrastructure 边界不被打破。
- 整合后仍不直接调用 LLM SDK、SQL、Milvus SDK 或具体 Agent 节点。
- 原 F1-F8 的页面入口能力仍可找到。

### TC-F9-120 视觉优化不降低可访问性和稳定性

**步骤**：
1. 在桌面宽屏和较窄窗口下查看页面。
2. 检查按钮、表格、图表、提示信息。

**预期结果**：
- 文本不重叠、不截断关键内容。
- 图表在不同宽度下仍可读。
- 按钮含义清楚。
- 色彩对比足够。
- 视觉优化不引入状态错乱或性能明显下降。

## 22. 自动化测试建议

### 22.1 Page Contract Tests

建议覆盖：

- 页面文件存在。

- 页面包含必要 Application 工厂调用。

- 调整预览写入 `pending_adjusted_plan`。

- 复盘 -> 调整预览 -> 保存。
- 当前计划 -> 导出。

## 23. 手动测试方案

### 23.1 Fake 手动流程

环境：

```env
USE_REAL_LLM=false
```


## 25. 完成定义

F9 完成需要满足：

- Streamlit 应用可以启动。
- 页面结构完整。
- 用户能从零开始完成主流程。
- F1-F8 能力在页面中连贯使用。
- 页面层不直接调用 LLM SDK、SQL、Milvus SDK 或具体 Agent 节点。
- 长任务有加载状态。
- 错误可理解，不展示原始 traceback。
- 关键操作更新 Session State。
- 刷新后能恢复最近计划。

- Real 环境有明确手动验收方案。

- 首页颜值高，并能清晰引导用户从零开始或继续已有计划。

- 页面是否整合经过信息架构判断，最终结构以用户使用舒适为准。
- 视觉优化不降低页面稳定性、可访问性和业务边界清晰度。

## 26. 风险与覆盖关系

| 风险 | 影响 | 覆盖用例 |
|---|---|---|
| 页面结构缺失 | 用户无法完成主流程 | TC-F9-001 到 TC-F9-008 |
| 页面直接依赖基础设施 | 难以测试和替换 | TC-F9-009 到 TC-F9-016 |
| Session State 混乱 | 跨页面状态丢失 | TC-F9-017 到 TC-F9-026 |
| 生成计划失败无提示 | 用户不知道如何恢复 | TC-F9-030 到 TC-F9-036 |
| 看板编辑未同步 | 复盘和导出数据不一致 | TC-F9-037 到 TC-F9-046 |
| RAG 页面不可用 | 资料能力断裂 | TC-F9-047 到 TC-F9-055 |
| 复盘指标不真实 | 用户误判进度 | TC-F9-056 到 TC-F9-065 |
| 导出不是当前计划 | 用户保存错误结果 | TC-F9-066 到 TC-F9-073 |
| 外部服务失败导致页面崩溃 | 产品不可用 | TC-F9-074 到 TC-F9-083 |
| Fake 演示不稳定 | 开发和 CI 受阻 | TC-F9-084 到 TC-F9-091 |
| Real 环境不可验收 | 无法上线演示 | TC-F9-092 到 TC-F9-101 |
| 中文乱码或布局破碎 | 用户体验差 | TC-F9-102 到 TC-F9-110 |
| 页面缺乏设计感 | 用户觉得产品粗糙、不可演示 | TC-F9-111 到 TC-F9-113 |
| 图表过于基础 | 用户难以理解进度和风险 | TC-F9-114 到 TC-F9-117 |

| 视觉优化影响稳定性 | 布局错乱或功能退化 | TC-F9-120 |
