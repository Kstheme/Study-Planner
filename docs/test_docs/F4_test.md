# F4 资料上传与问答测试用例

## 1. 测试目标

F4 的目标是让用户可以上传学习资料，系统解析、切分、向量化并保存到 Milvus，然后用户可以基于资料提问，系统回答并展示引用来源。

根据 `docs/PRD.md` 和 `docs/features.md`，F4 必须覆盖：

- 上传 PDF、Markdown、TXT、课程笔记
- 保存资料元数据
- 解析资料文本
- 文档切分
- 生成 embedding
- 写入 Milvus dense + sparse 混合索引
- 从 Milvus 使用混合检索召回相关资料片段
- 使用 RRF 融合 dense/sparse 排名
- 支持元数据过滤
- 支持查询改写、多查询分解和查询路由
- 可选支持重排和上下文压缩
- 基于资料回答问题
- 展示引用来源
- 资料摘要
- 概念解释
- 生成复习卡片
- 从资料中提取知识点

## 2. 测试范围

### 2.1 包含范围

- 资料上传用例
- 文件类型校验
- 文档解析
- 文档切片
- 向量库抽象接口
- Milvus 适配器，可先用 Fake VectorStore 测试
- RAG 问答服务
- 引用来源构造
- 摘要、概念解释、复习卡片、知识点提取
- Streamlit 资料问答页

### 2.2 不包含范围

- F2 学习计划生成
- F3 学习计划编辑
- F5 复盘重排
- 多用户资料隔离
- 复杂权限控制

## 3. 前置条件

F4 测试前建议准备：

- 一个 TXT 测试文件
- 一个 Markdown 测试文件
- 一个 PDF 测试文件
- 一段课程笔记文本
- Fake EmbeddingClient
- Fake VectorStore
- Fake LLM
- 可选：真实 Milvus 服务

测试默认优先使用 Fake 实现，避免依赖真实 Milvus 和真实 LLM。

## 4. 推荐领域模型

F4 至少需要以下模型：

- `LearningMaterial`
- `DocumentChunk`
- `MaterialQuestion`
- `MaterialAnswer`
- `Citation`
- `Flashcard`
- `KnowledgePoint`

建议字段：

### LearningMaterial

- `filename`
- `file_type`
- `source_path`
- `uploaded_at`
- `status`
- `chunk_count`

### DocumentChunk

- `id`
- `material_id`
- `text`
- `source`
- `page_number`
- `chunk_index`
- `metadata`

### MaterialAnswer

- `question`
- `answer`
- `citations`

### Citation

- `material_id`
- `filename`
- `chunk_id`
- `snippet`
- `page_number`
- `score`

## 5. 推荐抽象接口

F4 不应该让页面直接调用 Milvus 或 LLM SDK。

建议定义：

- `DocumentParser`
- `TextSplitter`
- `EmbeddingClient`
- `VectorStore`
- `HybridRetriever`
- `QueryRouter`
- `QueryRewriter`
- `Reranker`
- `ContextCompressor`
- `MaterialRepository`
- `RAGAnswerService`

## 6. 推荐检索策略

参考上传文档中的混合检索、查询构建、查询重写和进阶检索技术，F4 推荐采用以下检索策略。

### 6.1 默认检索：Milvus Hybrid Search

默认使用 Milvus 混合检索，而不是单一 dense vector 检索。

检索链路：

```text
用户问题
  -> Query Router
  -> Query Rewrite / Multi-query
  -> dense query embedding
  -> sparse query embedding
  -> Milvus dense search
  -> Milvus sparse search
  -> RRF 融合
  -> metadata filter
  -> optional rerank
  -> optional compression
  -> RAG answer with citations
```

选择原因：

- 学习资料里有大量专业术语，适合 sparse 精确匹配。
- 用户提问往往是自然语言，适合 dense 语义匹配。
- dense + sparse 可以同时提升召回率和准确率。
- RRF 不依赖原始分数，适合融合不同检索器结果。

### 6.2 元数据过滤

chunk 必须携带可过滤元数据：

- `material_id`
- `filename`
- `file_type`
- `source`
- `page_number`
- `section_title`
- `chunk_index`
- `tags`

需要支持：

- 按指定资料检索
- 按文件类型检索
- 按页码或章节检索
- 按标签检索

### 6.3 查询改写与多查询

需要支持：

- 简单问题直接检索。
- 模糊问题改写为更适合检索的问题。
- 复杂问题拆成多个子查询。
- 可选 HyDE：为抽象概念问题生成假设性答案后再检索。

### 6.4 查询路由

根据用户意图路由到不同能力：

- `qa`：资料问答
- `summary`：资料摘要
- `concept_explain`：概念解释
- `flashcard`：生成复习卡片
- `knowledge_points`：提取知识点

### 6.5 可选重排与压缩

MVP 默认使用 RRF。后续可选：

- LLM rerank
- Cross-Encoder rerank
- Contextual compression

测试中先用 Fake Reranker 和 Fake Compressor 验证接口，不强制依赖真实模型。

| 阶段 2 | 文档解析 |
| 阶段 3 | 文档切分 |

| 阶段 5 | 查询构建、改写与路由 |

| 阶段 9 | 异常与边界情况 |

## 8. 阶段 1：上传入口与文件校验

### F4-1-01 资料问答页可以正常打开

测试流程：

1. 打开 Streamlit 资料问答页。
2. 不上传任何资料。

预期结果：

- 页面正常加载。
- 显示资料上传控件。
- 显示资料列表区域。
- 显示问答输入框。
- 显示资料摘要按钮。
- 显示复习卡片生成按钮。

编写原因：

- 先保证页面基础可用。

### F4-1-02 支持上传 TXT 文件

测试流程：

1. 上传一个 `.txt` 文件。
2. 点击上传或处理按钮。

预期结果：

- 文件被接受。
- 创建 `LearningMaterial`。
- `file_type` 为 `txt`。
- 状态进入待解析或已解析。

编写原因：

- TXT 是最基础的资料格式。

### F4-1-03 支持上传 Markdown 文件

测试流程：

1. 上传一个 `.md` 文件。
2. 点击处理。

预期结果：

- 文件被接受。
- `file_type` 为 `markdown` 或 `md`。
- 能进入解析流程。

编写原因：

- 学习笔记常用 Markdown 格式。

### F4-1-04 支持上传 PDF 文件

测试流程：

1. 上传一个 `.pdf` 文件。
2. 点击处理。

预期结果：

- 文件被接受。
- `file_type` 为 `pdf`。
- 能进入解析流程。

编写原因：

- 课程资料和教材常用 PDF。

### F4-1-05 支持课程笔记文本输入

测试流程：

1. 在课程笔记输入框中粘贴一段文本。
2. 点击保存或处理。

预期结果：

- 文本被保存为 `LearningMaterial`。
- 来源类型为 `note`。
- 能进入切分和索引流程。

编写原因：

- 用户可能没有文件，只想粘贴笔记。

### F4-1-06 拒绝不支持的文件类型

测试流程：

1. 上传 `.exe`、`.zip` 或图片文件。

预期结果：

- 系统拒绝上传。
- 显示“不支持的文件类型”。
- 不创建资料记录。

编写原因：

- 防止无效文件进入解析流程。

### F4-1-07 上传成功后展示资料列表

测试流程：

1. 上传一个有效资料。
2. 查看资料列表区域。

预期结果：

- 显示文件名。
- 显示文件类型。
- 显示上传时间。
- 显示处理状态。
- 显示切片数量，若已处理。

编写原因：

- 用户需要知道哪些资料已经进入系统。

## 9. 阶段 2：文档解析

### F4-2-01 TXT 解析为纯文本

测试流程：

1. 准备 TXT 文件，内容为 Python 基础知识。
2. 调用 TXT parser。

预期结果：

- 返回文本内容。
- 中文不乱码。
- 空行处理合理。

编写原因：

- 保证基础文本资料可用。

### F4-2-02 Markdown 解析保留标题结构

测试流程：

1. 准备包含 `# 标题`、`## 小节`、代码块的 Markdown。
2. 调用 Markdown parser。

预期结果：

- 返回可检索文本。
- 保留标题文字。
- 代码块内容不丢失。

编写原因：

- 标题和代码块对学习问答很重要。

### F4-2-03 PDF 解析提取页面文本

测试流程：

1. 准备包含多页文字的 PDF。
2. 调用 PDF parser。

预期结果：

- 返回每页文本。
- 每段文本包含页码信息。
- 中文内容可读。

编写原因：

- 引用来源需要能显示页码。

### F4-2-04 空文件解析失败

测试流程：

1. 上传空 TXT 或空 Markdown。
2. 调用解析流程。

预期结果：

- 解析失败。
- 显示资料内容为空。
- 不写入向量库。

编写原因：

- 空资料不能产生有效问答。

### F4-2-05 解析失败时状态更新

测试流程：

1. 上传一个损坏 PDF。
2. 调用解析流程。

预期结果：

- `LearningMaterial.status` 变为 `failed`。
- 记录失败原因。
- 页面显示处理失败。

编写原因：

- 用户需要知道资料为什么不可用。

## 10. 阶段 3：文档切分

### F4-3-01 长文本可以切分为多个 chunks

测试流程：

1. 准备一段超过 chunk size 的长文本。
2. 调用 TextSplitter。

预期结果：

- 返回多个 `DocumentChunk`。
- 每个 chunk 有 `chunk_index`。
- 每个 chunk 有 `material_id`。

编写原因：

- RAG 检索依赖合理切片。

### F4-3-02 短文本只生成一个 chunk

测试流程：

1. 准备短文本。
2. 调用 TextSplitter。

预期结果：

- 返回 1 个 chunk。

编写原因：

- 短资料不应被无意义切碎。

### F4-3-03 chunk 保留来源信息

测试流程：

1. 对资料进行切分。
2. 检查每个 chunk。

预期结果：

- 包含文件名或 source。
- 包含 material_id。
- PDF chunk 包含页码，若可用。

编写原因：

- 引用来源依赖 chunk 元数据。

### F4-3-04 chunk 文本不能为空

测试流程：

1. 对含有多空行的文本切分。
2. 检查结果。

预期结果：

- 不产生空 chunk。

编写原因：

- 空 chunk 会降低检索质量。

### F4-3-05 chunk 顺序稳定

测试流程：

1. 同一份资料连续切分两次。
2. 比较 chunk_index 和文本。

预期结果：

- 顺序一致。
- chunk_index 一致。

编写原因：

- 稳定切分有利于测试和引用。

## 11. 阶段 4：向量化与 Milvus 混合检索

### F4-4-01 EmbeddingClient 能生成 dense 和 sparse 向量

测试流程：

1. 输入多个 chunk 文本。
2. 调用 Fake EmbeddingClient 或真实 BGE-M3 embedding。

预期结果：

- 返回 dense vectors。
- 返回 sparse vectors。
- dense 向量数量与文本数量一致。
- sparse 向量数量与文本数量一致。
- 每个 dense 向量维度一致。

编写原因：

- 混合检索需要同时具备语义向量和稀疏关键词向量。

### F4-4-02 HybridVectorStore 能写入 chunks

测试流程：

1. 准备 chunks、dense vectors 和 sparse vectors。
2. 调用 `HybridVectorStore.upsert()`。

预期结果：

- 写入成功。
- 返回写入数量或无异常。

编写原因：

- F4 要求写入 Milvus hybrid collection。

### F4-4-03 Dense 检索返回语义相关 chunks

测试流程：

1. 写入包含 Python 函数知识的 chunk。
2. 查询“如何定义可复用代码块”。

预期结果：

- 返回相关 chunk。
- 返回 score。
- 返回来源元数据。

编写原因：

- dense 检索负责语义召回，能处理用户问题和原文措辞不同的情况。

### F4-4-04 Sparse 检索返回关键词精确匹配 chunks

测试流程：

1. 写入包含“递归”“动态规划”“pytest”等关键词的 chunks。
2. 查询“pytest 怎么写测试”。

预期结果：

- 返回包含 `pytest` 的 chunk。
- 关键词匹配结果排名靠前。

编写原因：

- 学习资料中专业术语、函数名、库名需要精确匹配。

### F4-4-05 Hybrid 检索融合 dense 和 sparse 结果

测试流程：

1. Fake dense search 返回 A、B、C。
2. Fake sparse search 返回 C、D、A。
3. 调用 hybrid search。

预期结果：

- 返回融合后的结果。
- A 和 C 因同时出现在两路结果中排名靠前。
- 结果去重。

编写原因：

- 混合检索需要同时利用语义和关键词召回。

### F4-4-06 RRF 排序稳定

测试流程：

1. 构造两组不同顺序的搜索结果。
2. 使用 RRF 融合。

预期结果：

- 排名靠前的文档获得更高融合分。
- 同一输入多次融合结果一致。

编写原因：

- RRF 是 MVP 默认融合策略，需要可测试、可复现。

### F4-4-07 元数据过滤只返回匹配资料

测试流程：

1. 写入两个不同 `material_id` 的 chunks。
2. 查询时指定 `material_id=A`。

预期结果：

- 只返回 material_id 为 A 的 chunks。

编写原因：

- 用户可能只想问某一份资料。

### F4-4-08 元数据过滤支持文件类型

测试流程：

1. 写入 PDF 和 Markdown 两类 chunks。
2. 查询时指定 `file_type=pdf`。

预期结果：

- 只返回 PDF chunks。

编写原因：

- 查询构建需要支持按资料类型过滤。

### F4-4-09 检索结果可追溯到原文

测试流程：

1. 检索一个问题。
2. 查看返回结果 metadata。

预期结果：

- 包含 material_id。
- 包含 filename。
- 包含 chunk_id。
- 包含 snippet。
- PDF 包含 page_number，若可用。

编写原因：

- PRD 要求回答展示引用来源。

### F4-4-10 Milvus 不可用时错误清晰

测试流程：

1. 使用错误 Milvus 连接配置。
2. 执行 upsert 或 search。

预期结果：

- 抛出明确错误。
- 页面提示向量服务不可用。
- 不影响应用其它页面启动。

编写原因：

- 外部服务不可用时要可诊断。

## 12. 阶段 5：查询构建、改写与路由

### F4-5-01 简单问题直接检索

测试流程：

1. 输入问题：“Python 函数是什么？”
2. 调用 QueryRouter。

预期结果：

- 路由为 `qa`。
- 不触发复杂多查询分解。

编写原因：

- 简单问题应走低成本路径。

### F4-5-02 模糊问题会被改写

测试流程：

1. 输入问题：“这个怎么用？”
2. 当前上下文为“Python 函数”资料。
3. 调用 QueryRewriter。

预期结果：

- 输出更明确的问题，例如“Python 函数如何定义和调用？”

编写原因：

- 查询改写可以弥合用户短问题与资料表达之间的差距。

### F4-5-03 复杂问题拆成多个子查询

测试流程：

1. 输入问题：“递归和动态规划有什么区别，分别适合解决什么问题？”
2. 调用 MultiQueryRewriter。

预期结果：

- 至少生成 2 个子查询。
- 子查询分别覆盖递归、动态规划和适用场景。

编写原因：

- 多意图问题直接检索容易漏召回。

### F4-5-04 多查询结果会合并去重

测试流程：

1. 子查询 A 返回 chunk1、chunk2。
2. 子查询 B 返回 chunk2、chunk3。
3. 合并结果。

预期结果：

- 最终结果为 chunk1、chunk2、chunk3。
- chunk2 不重复。

编写原因：

- 多查询检索必须避免重复上下文。

### F4-5-05 查询路由到资料摘要

测试流程：

1. 输入：“总结这份资料”。
2. 调用 QueryRouter。

预期结果：

- 路由为 `summary`。

编写原因：

- 摘要不应走普通问答 prompt。

### F4-5-06 查询路由到概念解释

测试流程：

1. 输入：“解释一下递归”。
2. 调用 QueryRouter。

预期结果：

- 路由为 `concept_explain`。

编写原因：

- 概念解释需要更教学化的回答方式。

### F4-5-07 查询路由到复习卡片

测试流程：

1. 输入：“根据这份资料生成复习卡片”。
2. 调用 QueryRouter。

预期结果：

- 路由为 `flashcard`。

编写原因：

- 复习卡片有独立输出结构。

### F4-5-08 查询路由到知识点提取

测试流程：

1. 输入：“提取这份资料的知识点”。
2. 调用 QueryRouter。

预期结果：

- 路由为 `knowledge_points`。

编写原因：

- 知识点提取需要结构化输出。

### F4-5-09 HyDE 可生成假设性答案用于检索

测试流程：

1. 输入抽象问题：“为什么装饰器有用？”
2. 启用 HyDE。
3. 调用 QueryRewriter。

预期结果：

- 生成一段假设性答案文本。
- 后续使用该文本生成 dense query embedding。

编写原因：

- HyDE 适合抽象概念问题，能提升语义召回。

### F4-5-10 可选重排改变候选顺序

测试流程：

1. 初检返回多个 chunks。
2. Fake Reranker 给第二个 chunk 更高分。
3. 调用 rerank。

预期结果：

- 第二个 chunk 排到前面。

编写原因：

- 预留 rerank 能力，支持未来高精度检索。

### F4-5-11 可选上下文压缩减少噪音

测试流程：

1. 检索返回包含无关段落的长 chunk。
2. 调用 Fake ContextCompressor。

预期结果：

- 输出只保留与问题相关的句子。

编写原因：

- 压缩可以减少 LLM 上下文噪音和 token 成本。

## 18. 手动验收流程

### 18.1 Fake 模式验收

1. 打开资料问答页。
2. 上传 TXT 文件。
3. 上传 Markdown 文件。
4. 查看资料列表。
5. 点击处理资料。
6. 输入问题：“这份资料主要讲什么？”
7. 查看答案和引用来源。
8. 点击资料摘要。
9. 点击生成复习卡片。
10. 点击提取知识点。

通过标准：

- 上传成功。
- 资料被切分。
- Fake HybridVectorStore 能执行 dense、sparse 和 hybrid 检索。
- RRF 融合结果可见。
- Fake LLM 能回答。
- 页面显示引用来源。
- 摘要、卡片、知识点能展示。

### 18.2 真实 Milvus 混合检索验收

前置条件：

- Milvus 服务可用。
- `.env` 中配置：

```env
MILVUS_HOST=localhost
MILVUS_PORT=19530
MILVUS_COLLECTION=study_materials
RAG_RETRIEVAL_MODE=hybrid
RAG_RRF_K=60
```

流程：

1. 上传一份 TXT 或 Markdown。
2. 处理资料并写入 Milvus dense_vector 和 sparse_vector。
3. 输入与资料相关的问题。
4. 分别检查 dense、sparse、hybrid 检索结果。
5. 检查 RRF 融合结果。
6. 检查返回引用来源。

通过标准：

- Milvus hybrid collection 可写入。
- dense 检索返回语义相关 chunk。
- sparse 检索返回关键词匹配 chunk。
- hybrid 检索返回融合后的相关 chunk。
- citation 能追溯到原文件。

### 18.3 查询改写与路由验收

前置条件：

```env
RAG_ENABLE_QUERY_REWRITE=true
RAG_ENABLE_MULTI_QUERY=true
RAG_MULTI_QUERY_COUNT=3
```

流程：

1. 上传包含递归和动态规划的资料。
2. 输入复杂问题：“递归和动态规划有什么区别，分别适合解决什么问题？”
3. 检查系统生成多个子查询。
4. 检查多个子查询结果被合并去重。
5. 输入“总结这份资料”。
6. 检查路由为 `summary`。

通过标准：

- 复杂问题会拆成多个子查询。
- 检索结果去重。
- 摘要问题不会走普通 QA prompt。

### 18.4 真实 LLM 验收

前置条件：

`.env` 中配置真实 LLM：

```env
USE_REAL_LLM=true
DEEPSEEK_API_KEY=你的key
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash
```

流程：

1. 上传资料并完成索引。
2. 提问一个资料内问题。
3. 查看回答。
4. 查看引用来源。

通过标准：

- 回答内容与资料相关。
- 引用来源存在。
- 不回答资料外问题，或明确说明资料中没有相关内容。

## 19. F4 完成定义

F4 完成时必须满足：

- 用户能上传 TXT、Markdown、PDF 或课程笔记。
- 系统能解析资料并切分为 chunks。
- chunks 保留来源信息。
- 系统能生成 dense 和 sparse embedding 并写入 Milvus。
- 系统默认使用 hybrid search + RRF。
- 系统支持元数据过滤。
- 系统支持查询改写和多查询分解。
- 系统支持查询路由。
- 用户能基于资料提问。
- 回答能展示引用来源。
- 没有资料或检索不到内容时不会编造答案。
- 用户能生成资料摘要。
- 用户能生成复习卡片。
- 用户能提取知识点。
- 页面层不直接调用 Milvus SDK 或 LLM SDK。
